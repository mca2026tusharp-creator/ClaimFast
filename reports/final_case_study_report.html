Executive summary

ClaimFast turns free-form motor-insurance claim messages into a fixed nine-field JSON record for downstream review. The verified development bundle contains 100 planned observations (five prompts × 20 records × one run): 99 valid results and one invalid Prompt C result. No planned observations are missing. On the common 12-record non-example development view, A and all three B variants tie at 1.000 claim-type and urgency accuracy; C is 0.917 on both. Few-shot gains over A and a benefit from reasoning are not demonstrated by these results.

This is a development debugging result, not a held-out evaluation, safety certification, or release decision. A is a reasonable control for a future test because its development scores tie the smaller few-shot variants while using fewer mean input tokens; no strategy is approved for production.

1. Problem and business context

Claim intake messages may combine incident details, administrative questions, and missing or conflicting information. The prototype standardizes first-pass claim classification and extraction for a human-reviewed workflow. It predicts claim type and urgency and extracts policy number, incident date, location, vehicle registration, estimated amount, injury status, and police-report status.

The experiment measures structured prediction on synthetic messages. It does not measure customer outcomes, processing-time reduction, cost savings, or a live workflow.

2. Dataset and labeling approach

The project has 20 development records and 60 held-out records (80 total). An offline structural validation found all 80 JSONL records valid, with the same nine label fields in each. Dataset tag metadata records the required variety, including typos, missing fields, Hinglish, multi-incident messages, forwarded chains, ambiguous theft/glass cases, and short/long messages. The held-out file was not used for prompt tuning; no held-out model metrics are reported here.

Development label counts are own damage 5, third-party liability 4, theft 3, total loss 2, glass only 2, and not a claim 4; urgency counts are high 6, medium 10, and low 4. Labels are first-pass synthetic labels under the project’s operational labeling guide. Its interpretations are provisional. No independent second-review evidence for at least 20 labels was found. The concise one-page reviewer guide is prepared, and a blank 20-record worksheet is available; neither constitutes a completed human review. Conflicts still need a signed-off adjudication policy.

The common dev_eval view removes the union of the development examples used in the B prompts and contains 12 records. The all view contains all 20 and therefore includes prompt examples. Both views are development-only.

3. Prompt strategies and experiment configuration

Prompt Strategy
A Zero-shot task instructions and schema; no worked examples.
B-k3 Three nested development examples: DEV-01, DEV-06, DEV-17.
B-k5 B-k3 plus DEV-10 and DEV-14.
B-k8 B-k5 plus DEV-11, DEV-03, and DEV-09.
C Requests a concise evidence summary followed by a <final_json> block.

The library contains A, B-k3, B-k5, B-k8, and C. D is optional and was not implemented. The rubric asks few-shot examples to cover all classes: k=3 covers three of six claim types, k=5 covers five, and k=8 covers all six. Because each example has exactly one claim-type label, covering six classes requires at least six examples. Thus literal all-class coverage for k=3 and k=5 is mathematically impossible without changing the requested k or the single-label task. The current C prompt requests an evidence summary, not the rubric’s step-by-step chain-of-thought format. A separately versioned evidence-summary candidate is provided for review, but it is untested and is not equivalent to hidden chain-of-thought. The evaluated baseline prompt files were not changed.

All variants used openai/gpt-oss-120b, temperature 0, maximum 800 output tokens, low reasoning effort, hidden reasoning format, and one run. Examples were selected from development records only. The output must contain exactly nine schema fields. An unusable response remains an invalid prediction in the denominator rather than being dropped.

5. Error analysis

The only invalid stored result is dev|DEV-20|C|1. It failed the required exactly-one-<final_json>-block contract; parse and schema checks are false. It remains an invalid prediction for claim type, urgency, and extracted fields, not a missing observation. No raw response body is reproduced.

DEV-13 has a strict location mismatch for all five prompts but passes the lenient location rule. B-k8 also has one injury_reported exact mismatch on DEV-12. No other valid classification or extraction mismatches were identified.

6. Findings and decision questions

  • Does few-shot beat zero-shot? Not in these data. A, B-k3, and B-k5 tie on classification and all reported field metrics; B-k8 has the additional injury-field mismatch.
  • Does increasing k from 3 to 5 to 8 improve accuracy? No classification improvement is observed. Increasing to k=8 did not improve scores and coincides with the single B-k8 injury mismatch; this sample cannot establish a causal prompt effect.
  • Does reasoning help ambiguous or multi-incident messages, and is its extra cost justified? Not established. Prompt C is an evidence-summary prompt rather than the specified step-by-step CoT prompt, there is no controlled case-level benefit analysis, it has one invalid response, and no dollar cost is available.
  • What should serve 5,000 messages/day? Do not ship any prompt on this evidence. Carry A as a simple control into the required held-out and load-tested comparison: it ties A/B classification performance while having the lowest measured input-token use and latency here. This is a candidate for testing, not a production recommendation.

7. Proposed production strategy and guardrails

Keep the model behind a controlled intake service and use schema validation before downstream processing. Reject malformed or unsupported outputs; route invalid responses, unresolved conflicts, and high-risk cases to a trained reviewer. Do not convert an invalid response into confident nulls. Log prompt/model versions and operational metrics with appropriate data controls. Monitor parse/schema rates, injury and high-urgency false negatives, identifier hallucinations, latency, throughput, and token use. Before a 5,000-message/day deployment, complete held-out evaluation, independent label review, load/capacity testing, and a cost measurement using approved prices. The schema has no abstention/confidence field, so any confidence gate or abstention workflow needs a separately approved design.
